# Data2Decision: Project Description Analyzer (NLP)

This project is a professional Machine Learning system designed to analyze GitHub project descriptions (like READMEs) and provide intelligent career insights. It identifies core skills present in a project and suggests missing skills or new projects to improve a developer's portfolio.

## 📁 Project Structure

```text
project_root/
│
├── data/
│   ├── raw/                # Original, immutable datasets
│   └── processed/          # Data transformed for model training
│
├── models/
│   ├── skill_classifier.pkl   # Multi-label classifier (OneVsRest + RandomForest)
│   └── tfidf_vectorizer.pkl   # TF-IDF vectorization model
│
```

### 🔹 Repository Structure Explanation

*   **data/raw vs data/processed**: We separate incoming raw data from the data prepared for the model to ensure a reproducible pipeline and protect the integrity of the original source.
*   **src/ modules**: Contains the functional logic of the project, including data handling, feature extraction, and the orchestration of the ML pipeline.
*   **models/**: Dedicated storage for serialized model artifacts. Centralizing these allows different versions to be managed independently of the source code.
*   **logs/**: Used to track the execution history and catch errors during training or inference.
*   **reports/**: Stores the final analysis results, accuracy reports, and any visual insights generated by the system.

---

### 🔹 Data Flow Mapping

The system follows a linear end-to-end pipeline:

1.  **Raw Data**: Fetched from `data/raw/`.
2.  **Preprocessing**: Text is cleaned and normalized in `data_preprocessing.py`.
3.  **Feature Engineering**: Cleaned text is converted to numerical vectors using TF-IDF in `feature_engineering.py`.
4.  **Model Training**: A Multi-label classifier is trained in `train.py`.
5.  **Evaluation**: Success metrics are calculated in `evaluate.py`.
6.  **Model Saving**: Trained objects are serialized to the `models/` directory.
7.  **Prediction**: New project descriptions are analyzed in `predict.py` using stored artifacts.
8.  **Recommendation**: Career insights are generated in `recommend.py` based on predicted skills.

---

### 🔹 Design Justification

*   **Raw and Processed Separation**: Maintaining a `raw/` directory ensures that the original data remains a "single source of truth." Processed data can be regenerated at any time using the preprocessing scripts, which prevents permanent errors during data cleaning from corrupting the source.
*   **Notebooks outside src**: Jupyter Notebooks are excellent for Exploratory Data Analysis (EDA) and prototyping, but they are difficult to version control and test. Keeping them separate from the `src/` directory ensures that the "production" code remains clean and maintainable.
*   **Models outside src**: Models are large binary artifacts, not source code. Storing them in a dedicated `models/` directory follows the separation of code and data principle, making it easier to manage model versions and deployment.
*   **Logs and Reports**: Professional systems require auditability. Logs provide transparency into system behavior during long-running tasks, while reports allow stakeholders to review model performance without digging into the code.
*   **Centralized config.py**: Hardcoding paths across multiple files is a major source of refactoring bugs. Using a `config.py` allows the entire project environment (paths, constants, hyperparameters) to be adjusted from a single location.

## Data Leakage Demonstration

### Leakage Type
Train-Test Contamination (via Feature Scaling)

### What Was Done Wrong
In the contamination scenario, `StandardScaler` was fitted and transformed on the **entire dataset** before performing the train-test split. This allowed the training process to "see" the mean and variance of the test data, leading to statistical contamination.

### Impact
Numerical leakage causes the model to have an unfair advantage, often resulting in **artificially high or deceptive accuracy** that will not persist when the model encounters real-world data from a different distribution.

### Fix
The correct workflow is to **Split first**, then fit the scaler ONLY on the training data. The test data should then be transformed using the statistics (mean/std) learned strictly from the training set.

### Key Learning
A Machine Learning model must only learn from information that would be available at prediction time. Any "look-ahead" into the test set's distribution violates the core principle of objective evaluation.

- **RMSE** is invariably higher than MAE (usually around ~20 in this demo).
- This indicates that while the average error is low, there are some "larger" outliers in the predictions that the squared-error penalty of RMSE is highlighting.

- **R² Score (0.98)**: Indicates that 98% of the target's variance is successfully explained by our features.

### Cross Validation
- **Mean MAE**: 16.35 ± 0.94

### Key Learning
- **Intuition**: MAE is the easiest metric to explain to non-technical users.

- **Holistic View**: Never rely on a single metric; use R² for variance and RMSE for outlier sensitivity.

## Evaluation using MSE and R²

### What is MSE?
- **Mean Squared Error**: Measures the average of the squares of the errors.
- **Penalty Mechanism**: By squaring the differences, MSE penalizes large mistakes much more heavily than small ones, making it ideal for detecting outliers.

### What is R²?
- **Coefficient of Determination**: Measures the proportion of the variance in the target that is predictable from the features.
- **Baseline Comparison**: An R² of 0 indicates the model is no better than guessing the mean (the baseline).

### Results
**Baseline:**
- **MSE**: 17,133.35
- **RMSE**: 130.89
- **R²**: ~0.00 (Zero predictive utility)

**Model:**
- **MSE**: 214.01
- **RMSE**: 14.62
- **R²**: 0.98 (Excellent fit)

### Interpretation
- **Lower MSE/RMSE**: Indicates that the model's predictions are tightly clustered around the true values.
- **Higher R²**: Confirms that the model successfully learned 98% of the data's structural relationships.

### Cross Validation
- **Mean R²**: 0.9873 ± 0.0028
- **Mean RMSE**: 14.66 ± 0.57
- **Stability**: The extremely low standard deviation in both R² and RMSE indicates a highly stable and reliable model.

### Key Insight
- **MSE** tells us the magnitude of the error (penalizing the "worst cases").
- **R²** tells us the overall "usefulness" of the model compared to a naive guess.
- Both must be used together to ensure the model is both accurate and consistent.

## Numerical Feature Scaling

### In This Project
- **No numerical features in raw dataset**: The primary data is unstructured text (GitHub READMEs).
- **Text is converted using TF-IDF**: This transforms words into a numerical representation.
- **TF-IDF already normalizes data**: The weighting scheme (TF * IDF) inherently accounts for document length and term frequency, making additional scaling like `StandardScaler` unnecessary and potentially harmful to sparsity.

### Scaling Decision
- **StandardScaler NOT applied** to the main multi-label classification pipeline.

### Demonstration
- A separate demonstration (`src/scaling_demo.py`) was implemented to show the effect of scaling on distance-based models like **Logistic Regression**.
- **Result**: Accuracy improved from ~81% to ~87% when scaling was applied to synthetic data with varied ranges, demonstrating that scaling improves optimization stability for gradient-based solvers.

### Leakage Prevention
- **Split before Scaling**: The `StandardScaler` is fitted only on the training set.
- **Transformed Test Set**: The test data is transformed using the mean and standard deviation learned strictly from the training data, preventing information from the future from entering the training process.

## Feature Normalization using MinMaxScaler

### In This Project
- **No numerical features present**: The raw dataset consists of textual descriptions.
- **Text is transformed using TF-IDF**: The resulting vectors already represent word importances in a normalized comparative scale.
- **TF-IDF already normalizes values**: Standard TF-IDF implementations in `scikit-learn` use L2 normalization by default.

### Why MinMaxScaler Not Used
- **NLP features already scaled**: Applying another scaling layer to TF-IDF sparse matrices is redundant.
- **No distance-based raw numerical features**: Our current Random Forest model is tree-based and does not rely on Euclidean distances.

### Demonstration
- A separate demonstration (`src/minmax_scaling_demo.py`) shows the effect of squeezing features into a **range of [0, 1]**.
- **Result**: Verification of `min=0.0000` and `max=1.0000` on the training set, ensuring correct boundary implementation.

### Leakage Prevention
- **Split before Scaling**: Scaling parameters were learned strictly from the training set.
- **Consistent Transformation**: The test set was transformed using the same scaler object without re-fitting.

### When to Use MinMaxScaler
- **Distance-based models**: k-Nearest Neighbors (kNN), Support Vector Machines (SVM).
- **Optimization stability**: Artificial Neural Networks (ANN) where consistent activation ranges improve backpropagation.

## Precision & Recall Evaluation

### What is Precision?
- **Precision**: Of all the projects the model *predicted* had the skill, how many *actually* had it? It's a measure of quality (avoiding False Alarms).

### What is Recall?
- **Recall**: Of all the projects that *actually* had the skill, how many did the model manage to *find*? It's a measure of quantity (avoiding Missed Cases).

### Results
**Baseline:**
- **Precision**: 0.00 (Usually 0 if majority is negative, or matches majority frequency)
- **Recall**: 0.00 (Usually 0 if majority is negative)

**Model:**
- **Precision**: 0.50
- **Recall**: 1.00

### Confusion Matrix Insight
- **True Positives (TP)**: Correctly detected the skill (e.g., Python).
- **False Positives (FP)**: False alarm (predicted a skill where none existed).
- **False Negatives (FN)**: Missed case (the skill existed but the model missed it).

### Trade-off
- **Increasing Precision**: Reduces False Positives but usually leads to more False Negatives (Missed Cases).
- **Increasing Recall**: Reduces False Negatives but usually leads to more False Positives (False Alarms).

### Key Insight
- Accuracy is misleading in imbalanced data because it hides the Recall failure for minority classes.
- Precision & Recall together show the true operational performance of the model.

- Missing a fraudulent transaction (False Negative) results in a massive loss of ₹50,000.
- A False Alarm (False Positive) only costs ₹1,000 to investigate (e.g., a simple phone call to the customer).
- We would much rather investigate 50 innocent customers than miss one thief. High Recall ensures we catch as much fraud as possible, even at the cost of some additional investigations.

### Threshold Explanation
- **Lower Threshold (e.g., 0.2)**: Boosts **Recall**. The model becomes "braver" and flags anything suspicious.
- **Higher Threshold (e.g., 0.8)**: Boosts **Precision**. The model becomes "cautious" and only flags when it is absolutely certain.

## F1 Score Evaluation

### What is F1 Score?
F1 is the **harmonic mean** of Precision and Recall. Unlike a simple average, the harmonic mean is very sensitive to low values; if either Precision or Recall is zero, the F1 score becomes zero.

### Why F1 is Important?
- **Accuracy Fails**: In imbalanced data, accuracy can look great while the model is actually failing.
- **Balanced Performance**: F1 ensures that the model is performing well on *both* catching all positive cases and ensuring those cases are truly positive.

### Results
**Baseline:**
- **F1-Score**: 0.00 (In most imbalanced real-world distributions where majority is negative)

**Model:**
- **F1-Score**: 0.67

### Interpretation
- **Model Improvement**: Our Logistic Regression model achieved a significantly higher F1-score than the baseline, proving it has learned to identify skills with a solid balance of precision and recall.
- **Harmonic Penalty**: Since our F1 is 0.67, it confirms that neither precision nor recall dropped to an unacceptable level.

### Key Insight
- **F1 Punishes Imbalance**: You cannot have a high F1-score if you have a "Recall of 1.0 but Precision of 0.01".
- **High F1 = Good Model**: A high F1-score is often the strongest single indicator that your classification model is reliable and ready for deployment.

## KNN Model

### What is KNN?
- **Instance-Based Learning**: Also known as "Lazy Learning," KNN doesn't learn a global model. Instead, it memorizes the training data and finds the "K" most similar records during prediction.
- **Simplicity**: It makes no assumptions about the data distribution (non-parametric).

### Why scaling?
- **Distance-Based algorithm**: KNN relies on Euclidean distance (straight-line distance).
- **Dominance Correction**: Without scaling, features with large numeric ranges would dominate the distance calculation, making features with small ranges (but high importance) effectively invisible to the model.

### Best K
- **GridSearchCV**: We used cross-validation to test multiple values of K (1 through 20).
- **Selection**: The K that provided the most stable generalization across different data chunks was selected as the optimal hyperparameter.

### Results
- **Baseline Accuracy**: 0.5000
- **KNN Accuracy**: 0.5000 (Small sample limitation)
- **Best K**: 1 (Selected based on project distribution)

### Interpretation
- **Small K (e.g., 1)**: Highly sensitive to noise. The model might overfit to individual outliers.
- **Large K (e.g., 20)**: Smoothes over the logic. The model might underfit and just predict whatever class is more frequent overall.

### Final Insight
- **KNN is ideal for small, well-separated datasets** but struggles significantly as the number of features increases (high dimensions) or label boundaries become complex and overlapping.

## Video Answers: KNN in Production

### Q: Scenario with 60 features and 50,000 samples
**👉 Problems:**
- **Curse of Dimensionality**: In 60D space, all points become "distant" from each other, making the "nearest" neighbor less meaningful.
- **Slow Prediction**: Since KNN is a lazy learner, it must search through 50,000 points *for every single prediction*. This creates massive latency.
- **Unstable CV**: With high feature count, a small change in training data can wildly shift which neighbors are "nearest."

**👉 Answer:**
**NOT suitable for production.**

**Why?**
- **Distance becomes meaningless**: The "closeness" signal is drowned out by the volume of dimensions.
- **Prediction slow**: The O(N) complexity for every prediction makes it impossible to scale for real-time applications.

- **Solution**: Use PCA for dimensionality reduction or switch to a faster "eager learner" like Logistic Regression.

## Decision Tree Model

### What is a Decision Tree?
- **Flowchart Logic**: Learns by repeatedly asking binary questions ("Is feature X > threshold?") to partition the data into rectangular regions.
- **Natural handling of features**: It doesn't require scaling and handles non-linear relationships and feature interactions automatically.

### Why Scaling is NOT required?
- **Rank-Based Splitting**: Decision trees only care about the *order* of values, not their magnitude. A split point is chosen based on how well it separates classes, regardless of whether the feature is scaled or not.

### Hyperparameter Tuning: Depth Selection
- **Overfitting Warning**: Unconstrained trees (max_depth=None) grow until every leaf is pure, often reaching 100% training accuracy but failing on new data.

## Video Answers: Accuracy & Reliability

### Q1: Why is baseline accuracy misleading?
**👉 Dataset is imbalanced.** The majority class dominates the total count. A model could be perfectly accurate on the majority while being 100% wrong on the minority, making it a failed model despite a high accuracy score.

### Q2: Is the model better if accuracy stays the same?
**👉 YES.** If the **Recall or F1-score** improved, the model is significantly better because it is actually learning to distinguish between classes rather than just sticking to the majority.

### Q3: Why does accuracy barely change after training?
**👉 Small Minority Class.** If the class we are trying to predict is very small (e.g., 2% of the data), even big improvements in finding those samples won't move the overall accuracy number much.

### Q4: What is the most important metric?
**👉 It depends on the problem.** If you can't afford to miss a skill (e.g., matching a candidate to a job), **Recall** is most important. If you can't afford false matches, **Precision** is most important. F1 typically provides the best compromise.

### Q5: Should we deploy based only on Accuracy?
**👉 ❌ No.** Accuracy is a "shallow" metric. Without checking stability (Cross-validation) and error types (Confusion Matrix), you risk deploying a model that fails completely in the real world.

## Video Answers: Feature Importance Deep Dive

### Q: Why is CustomerID high in MDI but 0 in permutation?
**👉 Answer:**
- **High-Cardinality Bias**: Each CustomerID is unique. A Decision Tree can use these unique IDs to create perfect splits that isolate individual training samples (Memorization). This leads to a massive reduction in impurity (High MDI). 
- **Overfitting**: However, CustomerID has zero relation to the actual project skills.
- **Not useful for generalization**: When you permute (shuffle) CustomerID in the test set, the model's accuracy doesn't drop because a *new* CustomerID in the test set doesn't exist in the training rules anyway.

### Should we remove CustomerID?
**👉 YES.** It is a non-predictive feature that increases model complexity and risks "leakage" if the IDs are sequentially assigned.

### Which method is better for feature selection?
**👉 Permutation importance.** It protects you from the cardinality bias of MDI and ensures you only keep features that have a measurable impact on unseen data.
